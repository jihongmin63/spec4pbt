# 생성 계획을 표현하고 조합하는 자료구조

## 현재 논의 상태

**여러 부품의 ensure로 한 부품의 require를 해소하는 조립 방향은 사용자와 합의했다.
생성기 계획 부품의 상세 정의와 자료구조는 아직 확정하지 않았다.**
[이전 분해 계획](generator-decomposition.md)을 참고하되, 그 문서의 순차 단계와 뒤에서 앞으로
조건을 전달하는 방식을 일반적인 조립 규칙으로 확정하지 않는다.

현재 조립 논의의 기준은 다음과 같다.

- 부품 조립의 의미를 판단하는 중심은 `require`와 `ensure`다. 아래 후보 자료구조에서는 각각
  `requires`, `ensures`라는 필드명을 사용하지만, 그 필드 구성도 확정된 것은 아니다.
- 최종 생성기 계획에는 남은 `require`가 없어야 하며, `ensure`로 원래의 모든 premise를
  만족해야 한다. 논리식으로는 최종 요구가 `True`인 닫힌 계획을 목표로 한다.
- 여러 생성기 계획 부품이 한 부품으로 연결될 수 있다. 조립을 하나의 깔끔한 sequential로
  제한하지 않는다. 실행 순서의 표현과 계약을 연결하는 구조는 구분해서 논의한다.

**Soundness와 completeness는 지금 논의하지 않는다.** 우선 require와 ensure만으로
부품을 어떻게 연결하고, 합친 계획을 어떻게 표현할지 다룬다. 각 부품의 ensure를 정확한 생성
범위로 볼지와 증명 의무의 배치도 보류한다.

## 현재 조립 방식

부품은 자신의 `require`가 충족되면 `ensure`를 제공한다. 연결할 때에는 하나 이상의 부품이
제공하는 ensure를 함께 사용하여 다른 부품의 require를 충족한다.

예를 들어 A와 B가 C로 합류한다면, 실제 연결되는 값들에 대해 다음 관계를 사용한다.

```text
ensure_A ∧ ensure_B ⇒ require_C
```

A나 B 하나가 C의 요구 전체를 충족할 필요는 없다. 두 보장이 함께 요구를 충족하면 된다.
이 연결은 A와 B를 반드시 한 줄로 이어야 한다는 뜻이 아니다. 한 부품의 ensure를 여러 부품이
사용할 수도 있다. 조건에 등장하는 값의 연결과 같은 값 사이의 관계는 유지한다.

조립한 계획도 남은 require와 확보하는 ensure로 요약한다.

- 내부에서 충족한 require는 조립된 계획의 외부 요구로 남기지 않는다.
- 아직 충족하지 못한 require는 남겨 둔다. A와 B 자체의 require도 조립만으로 사라지지 않는다.
- 남은 require가 충족된다는 조건 아래에서, 연결된 부품들이 제공하는 ensure를 함께 사용한다.
  require를 해소해도 그 근거로 사용한 ensure가 소모되는 것은 아니다.

한 부품의 ensure를 사용하면서 그 부품 자체의 require를 빠뜨려서는 안 된다. 서로의 ensure를
순환해서 인용하는 것만으로 모든 require가 해소된 것으로 처리하지 않는다.

이 조립을 통해 최종적으로 **남은 require가 없고, ensure로 원래의 모든 premise를 만족하는
하나의 생성기 계획**을 만든다. 이를 저장할 필드 구성과 구체적인 조립 연산은 계속 논의한다.

## 이전 후보 상세 — 보류

아래의 `Plan`·`Group`, `order`·`members`, 순차 연결 규칙과 증명 관련 내용은 이전 후보를
참고용으로 보존한 것이다. 현재 합의된 조립 방향에 맞춰 다시 검토해야 하며, 이번 논의의
필수 조건이나 확정된 인터페이스로 취급하지 않는다. 생성기 구현과 증명에 관한 논의도 보류한다.

### 목적과 범위

**Agent가 생성 계획을 자유롭게 분해하고, 부품의 계약과 연결을 명확히 기록할 수 있는 자료구조를
검토한다.** 생성 전략을 찾아내는 절차나 지원할 분해 작업의 목록은 정하지 않는다.
Agent가 생성 가능성과 구현 방법을 충분히 고려하도록 하는 작성 지침은 후속 논의 대상으로 둔다.

목표는 원래 `Contract.Premise`를 만족하는 입력만 만들고, 그런 입력을 빠짐없이 만들 수 있는
생성기를 부품별로 작성하는 것이다. 부품별 soundness·completeness는 생성기를 작성한 뒤
그 구현이 자기 계약을 정확히 따르는지 증명한다.
검증된 부품들을 연결하면 공통 조합 정리로 더 큰 검증된 부품을 얻는다. 원래 premise와의 대응은
최종 합성 계약에서 확인하며, 부품마다 원래 premise 전체를 다시 증명하지 않는다.

분석과 계획은 같은 값·조건 ID를 사용하는 하나의 그래프로 관리한다. 기존의 값, 조건, 그룹 구조를
유지하고 초기 정보, 합성 부품의 경계, 최종 목표, 증명 선언의 연결을 명시한다.
아래는 논리적인 자료구조다. JSON 등의 저장 형식과 구체적인 CLI는 구현 시 정한다.

현재는 자료구조와 검증 경계를 논의하는 단계이며, 부품 정의나 조립 규칙이 확정되지 않았다.
실제 생성 계획이나 증명이 완료되었다는 뜻도 아니다. 거절 생성 여부에 대한 별도 감사 설계는 이번 범위에서 제외한다.
기존 `emit/check/run`의 인증 기준은 유지한다.

### 역할과 작업 흐름

전체 작업은 전제 분석, 계약 확정, 부품 구현, 전체 조합·인증의 네 단계다.
이 자료구조는 특히 두 번째 단계에서 Agent가 부품과 연결을 명확히 기록하는 데 초점을 둔다.

| 작업 | Agent | 도구 |
| --- | --- | --- |
| 전제 분석 | 필요한 값과 조건의 상세 분석 요청 | 명세의 값·조건·출처와 참조 관계 추출 |
| 계획 작성 | 부품 경계, 입출력, 계약, 조립, 생성 방법 결정 | 자료구조 편집과 구조 검사 지원 |
| 계약 조합 | 연결과 계약의 정당성 증명 작성 | 연결 의무 생성, 합성 계약 계산, Lean 증명 검사 |
| 목표 대응 | 최종 합성 계약과 원래 premise의 동치 증명 작성 | 정확한 목표에 대한 증명인지 검사 |
| 부품 구현 | 생성기를 작성한 뒤 해당 구현의 soundness·completeness 증명 | 컴파일과 증명 검사 |
| 전체 인증 | 결과와 실패 원인 검토 | 검증된 부품의 조합 정리 적용과 기존 `check` 실행 |

계약만 먼저 조합하여 원래 premise와의 대응을 확인할 수 있어야 한다. 생성기를 연결하는 단계는
같은 부품 구조를 사용한다. 계획 작성 중의 탐색 순서는 Agent에게 맡긴다. 뒤 부품의 요구를 앞
부품의 보장에 반영하는 방법도 사용할 수 있지만, 자료구조가 이를 유일한 설계 절차로 강제하지 않는다.

### 전체 자료구조

```text
Plan
  target        원래 입력 타입·premise·출처와 최종 출력 값 ID
  initial       주어진 값의 바인딩과 사용 가능한 사실
  values        Value ID → Value
  constraints   Constraint ID → Constraint
  groups        Group ID → Group
  root          최종 부품의 Group ID
  evidence      증명 의무 ID → Lean 선언 참조
```

`target`은 기존 property에서 정해진 `Contract.Input`과 `Contract.Premise`를 가리킨다.
편집 가능한 계획에서 다른 조건을 적는 것으로 목표를 바꿀 수 없다. 원본과 번역의 정체성도
연결하여, 어떤 명세에 대한 계획인지와 변경 후 재검사가 필요한지를 판단할 수 있어야 한다.
최종 출력 값은 `Contract.Input` 타입이며 `root`의 외부 출력으로 제공한다.

`initial`에는 실제로 주어진 값의 표현 또는 매개변수 바인딩, 그 값에 대해 사용할 수 있는 사실을
기록하는 후보를 둔다. 이 정보를 사용하는 경우에도 최종 계획에 미해결 요구를 남기지 않아야 한다.
생성하기 편하도록 새로운 가정을 추가하거나 원래 입력 범위를 줄이지 않는다. 최종 목표의
매개변수가 있다면 계약과 목표를 같은 매개변수 아래에서 비교한다.

`evidence`에는 선언 위치만 저장한다. 증명 의무의 명제는 계약과 연결 구조에서 도구가 도출한다.
선언이 적혀 있다는 사실이나 저장된 성공 표시를 증명 완료로 신뢰하지 않는다.

### 값과 조건

```text
Value
  id
  type
  scope
  origin

Constraint
  id
  expression
  scope
  origin
```

`id`는 계획 안에서 고유한 항목을 식별하고, `scope`는 그 바인딩이나 조건의 유효 범위를 나타낸다.
`origin`은 원래 명세의 선언·변수·필드·조건 위치 또는 Agent가 추가한 항목의 출처다.
같은 출처를 가리킨다는 이유만으로 두 값이 같아지는 것은 아니다.
원래 입력의 존재 증인과 생성용 보조 값도 이 구조로 기록하며, 최종 입력과 구별한다.

예를 들어 최종 쌍 `x`의 첫 성분에 넣을 부분 값 `a`는 `origin = x의 첫 성분`을 가질 수 있다.
그러나 `a`라는 바인딩과 완성된 `x`의 필드 참조는 다르다. `x := (a,b)`라는 조립이 둘을 연결한다.
분석에서 필드 노드를 펼친 것만으로 부모 값이 생성되거나 이 대응이 증명되었다고 보지 않는다.

`expression`은 타입과 변수 바인딩이 확인되는 식이다. 명세에서 온 식의 논리 구조를 보존하고,
추가 조건은 Lean 정의·관계의 적용 등을 통해 표현할 수 있다. 계약의 의미를 설명문 문자열로
대신하지 않는다. 표현식의 구체적인 직렬화는 구현 세부사항이며 분해 전략의 허용 목록이 아니다.

조건은 conjunction, 대안, 양화, 관계 호출과 그 범위를 보존한다. 순서가 의미에 영향을 주는
명세 규칙도 유지한다. 값을 참조하지 않는 조건도 보존한다. 같은 값이 식에 여러 번 등장하면
각 참조 위치를 유지하며, 자유 변수와 그래프의 연결은 식에서 계산한다.

Agent는 지정한 값이나 조건 아래만 추가로 펼칠 수 있다. 기존 ID와 의미는 유지하고 필요한
세부 항목을 추가한다. 원본에서 재구성되는 분석 정보와 Agent가 작성한 계약·보조 정의는 출처로
구별한다. 분석의 세밀함과 생성 부품의 크기는 별개다.

### 기본 부품과 합성 부품

아래는 순서를 둔 그룹 구조의 후보이며, 여러 부품이 한 부품의 요구를 함께 충족하는 조립을
어떻게 표현할지는 다시 논의한다. `order`나 부모·자식 포함 관계를 조립의 필수 형태로 확정하지 않는다.

```text
Group
  id
  order
  inputs
  outputs
  requires
  ensures
  assembly
  construction
  members        기본 부품이면 없음, 합성 부품이면 자식 Group ID들
  generator      선택적인 Lean 생성기 선언 참조
```

기본 부품과 합성 부품은 같은 인터페이스를 사용한다. `members`만 내부 구성을 나타낸다.
합성 부품도 다른 합성 부품의 자식으로 사용할 수 있다. 각 그룹은 `root` 아래의 한 위치에 속한다.
같은 생성 방법을 여러 위치에서 재사용하려면 별도 그룹 인스턴스를 만들고 같은 Lean 정의를 참조한다.
이 포함 관계와 값의 참조 관계는 다르다. 한 부품이 제공한 값을 여러 뒤 부품이 사용하는 것은 허용한다.

`order`는 같은 부모 아래에서 중복 없는 정수이며 작은 값부터 실행한다. 루트에는 필요하지 않다.
자식 목록의 저장 위치나 다른 합성 부품 내부의 번호와 혼동하지 않는다. 그룹 ID는 순서를 바꾸어도
유지한다. `members`에 순환을 만들 수 없으며, 합성 부품을 실행할 때 자식과 부모를 중복 실행하지 않는다.

| 항목 | 의미 |
| --- | --- |
| `inputs` | 부품 밖에서 받아야 하는 값 ID들 |
| `outputs` | 부품 밖으로 제공할 값 ID들 |
| `requires` | 입력에 대한 요구 조건 ID들. 목록은 conjunction으로 해석한다 |
| `ensures` | 입력과 출력에 대한 정확한 출력 조건 ID들. 목록은 conjunction으로 해석한다 |
| `assembly` | 새 출력 값 ID와, 이미 확보된 값들로 그 값을 만드는 타입이 있는 조립 식 |
| `construction` | 생성 방법에 관한 Agent의 설명과 관련 정의 참조. 형식 증명의 대체물이 아니다 |
| `generator` | 기본 부품의 구현 선언. 구현 전에는 비워 둘 수 있다 |

합성 부품의 생성기는 자식 생성기와 조립 식에서 도구가 도출한다. 생성된 선언을 참조할 수 있지만
`members`와 별개의 구현을 수작업으로 지정해 내부 구성을 바꾸지는 않는다.

목록 안의 개별 조건은 대안이나 양화 등 임의의 논리 구조를 포함할 수 있다. 단순한 조건 목록으로
표현하기 어려운 계약은 하나의 이름 붙은 조건으로 표현한다. 새로운 생성 방법을 사용하기 위해
도구에 새로운 분해 명령을 추가할 필요는 없다.

`requires`의 자유 변수는 입력에서, `ensures`의 자유 변수는 입력과 출력에서 확보되어야 한다.
증인이나 내부 보조 값이 외부 계약에 필요하면 양화하거나 명시적인 출력으로 제공한다.
부품 내부의 값이 외부 계약의 숨은 자유 변수로 남아서는 안 된다.

#### 값의 연결과 외부 출력

자식은 부모의 입력과 앞 자식이 제공한 출력을 사용할 수 있다. 같은 값 ID를 사용하면 같은
바인딩을 전달한다. 다른 이름이나 표현으로 바꾸려면 조립·계산과 그 대응을 명시한다.
값의 제공자는 입출력과 포함 관계에서 계산하므로 별도 연결 목록으로 중복 저장하지 않는다.

한 값 ID를 두 기본 부품이 독립적으로 생성할 수 없다. 합성 부품의 출력에 자식의 출력 ID가
나타나는 것은 그 값을 외부로 전달한다는 뜻이며 다시 생성한다는 뜻이 아니다.
부모 값을 조립할 때에는 기록된 부분 값을 사용하고 조립 식의 의존 순서를 따른다.

합성 부품의 `outputs`는 내부에서 만든 값 중 어떤 값을 밖에 내보낼지 결정한다. 뒤에서 필요한
값은 이 경계를 통해 전달한다. 외부로 제공하지 않은 내부 값은 합성 계약에서 존재 양화한다.
내부 값의 타입이 다른 내부 값에 의존한다면 의존 순서를 유지해 함께 양화한다.

기존 입력을 그대로 외부에 제공하는 것도 허용한다. 부품은 입력을 몰래 수정하지 않는다.
환경을 갱신하면 `c`에서 `c'`를 계산하는 관계처럼 서로 다른 바인딩으로 기록한다.

#### 분기·반복·재귀를 담는 방법

분기나 반복을 포함한 생성 방법도 기본 부품의 계약과 Lean 구현으로 표현할 수 있다.
Agent가 원하면 더 작은 부품으로 나누고, 그렇지 않으면 하나의 부품으로 유지한다.
자료구조가 모든 명령어·반복 회차·규칙 대안을 개별 그룹으로 펼치도록 요구하지 않는다.

`members`는 순서대로 연결하는 내부 구성을 표현한다. 대안 중 하나를 선택하거나 목록을 반복
생성하는 방법을 모든 자식의 순차 실행으로 오해하지 않는다. 이런 제어는 해당 부품의 정의에 두고
계약과 증명으로 검사할 수 있다. `members`의 순환을 생성기 재귀 표현으로 사용하지 않는다.

### 계약의 의미와 연결 규칙

이 절은 기존 순차 조립 후보를 설명한다. 여러 부품의 보장을 함께 사용하여 한 부품의 요구를
충족하는 일반적인 규칙, 그리고 soundness와 completeness 의무의 분리는 아직 확정하지 않았다.

부품의 입력을 `s`, 출력을 `t`라고 할 때 계약을 다음처럼 해석한다.

```text
R(s)    = requires
E(s,t)  = ensures
```

계획 단계에서는 이 계약과 부품 분해의 정당성을 확인한다. **기본 부품의 생성기를 작성한 뒤**,
그 구현에 대해 다음 두 의무를 증명한다. 생성기 없는 계약만으로 구현의 증명을 완료했다고 하지 않는다.

```text
soundness: R(s) → (Gen.support (generate s) t → E(s,t))
completeness: R(s) → (E(s,t) → Gen.support (generate s) t)
```

`ensures`는 참고용 사후 조건이 아니라 생성해야 하는 출력의 정확한 범위다. 유용한 추가 조건을
계약에 넣는 것은 허용하지만, 최종 목표와의 동치를 증명해야 하므로 원래 유효한 입력을 임의로
제외할 수는 없다.

`R(s) → ∃ t, E(s,t)`는 별도 필수 증명 의무로 두지 않는다. 현재 `Gen`은 support가 비어 있는
생성기도 표현하므로 생성기 코드가 있다는 사실만으로 출력 존재가 보장되지는 않는다.
유효한 출력이 주어지면 구현 후의 completeness가 그 출력의 생성 가능성을 보장한다.
이 설계는 모든 허용 입력에서 support가 비어 있지 않다는 별도 보장이나, 유한한 샘플링 자원에서의
성공 보장을 추가하지 않는다.

#### 하나의 부품을 여러 부품으로 나눌 때

이미 계약을 정한 부모 부품 C를 A와 B로 나눈다고 하자. C의 `inputs`, `outputs`, `requires`,
`ensures`는 유지하고, 내부에 A와 B의 계약·실행 순서·값의 연결·조립 식을 추가한다.
자료구조에서는 C의 `members`에 A와 B를 기록한다. 분해를 이유로 부모 계약의 의미를 바꾸지 않는다.

```text
분해 전: C가 입력을 받아 부모 계약에 맞는 결과를 제공한다.
분해 후: 같은 입력을 A, B가 나누어 처리하고, 결과를 조립하여 C의 출력으로 제공한다.
```

분해 단계에서는 다음을 확인한다. 모두 부모의 `requires`를 만족하는 입력에 대한 의무다.

1. **자식의 요구를 충족한다.** 부모의 입력 조건으로 첫 자식의 `requires`를 만족해야 한다.
   이어서 앞 자식들의 `ensures`를 가정하면 다음 자식의 `requires`를 만족해야 한다.
   앞 자식들이 허용하는 모든 결과에 대해 확인하며, 특정한 좋은 중간 값 하나만 고르지 않는다.
   필요한 값이 해당 시점에 제공되는지와 타입이 맞는지도 검사한다.
2. **조립 결과가 부모 조건을 만족한다.** 자식들의 계약을 만족하는 결과를 조립하면 반드시
   부모의 `ensures`를 만족해야 한다.
3. **부모가 허용하던 결과를 빠뜨리지 않는다.** 부모의 `ensures`를 만족하는 결과 하나를
   임의로 주었을 때, 그것을 조립할 수 있는 자식 결과들이 있고 각 자식의 계약을 만족해야 한다.

2와 3을 합치면 부모의 출력 조건과 자식 계약·조립으로 표현한 출력 조건의 동치가 된다.
이는 계약을 나눈 방법에 대한 증명이다. 아직 생성기가 존재하거나 그 구현이 올바르다고 주장하지 않는다.
3의 내부 값 존재는 이미 주어진 부모 결과를 표현할 수 있다는 뜻이며, 모든 입력에 부모 결과가
하나 이상 있다는 별도 출력 존재 의무와 다르다.

자식 A를 다시 더 작은 부품으로 나눌 때에도 A의 계약을 부모 계약으로 삼아 같은 세 항목만 확인한다.
각 분해에서 원래 `Contract.Premise` 전체와 다시 비교하지 않는다.

#### 분해 의무의 논리적 형태

C의 입력을 `s`, 출력을 `x`라고 하자. A는 `s`로부터 `t`를, B는 `s,t`로부터 `u`를 제공하고,
조립 식은 `x := f(s,t,u)`인 경우다. 아래에서 각 `R`은 해당 부품의 요구, `E`는 보장이다.

```text
첫 자식 진입:
  R_C(s) → R_A(s)

다음 자식 진입:
  R_C(s) ∧ E_A(s,t) → R_B(s,t)

분해 전후의 출력 조건 동치:
  R_C(s) →
    (E_C(s,x) ↔ ∃ t u, E_A(s,t) ∧ E_B(s,t,u) ∧ x = f(s,t,u))
```

이 명제들은 각각 모든 자유 변수에 대해 증명한다. 실제로 전달하는 입력이 다르면 그 바인딩에
맞춰 의무를 만든다. 요구와 보장에 같은 문자를 쓸 필요는 없고, 필요한 함의가 증명되면 된다.

#### 합성 계약

도구는 자식 계약과 조립 식으로부터 내부 연결을 나타내는 조건을 계산한다. 외부에 드러나지 않는
중간 값은 존재 양화하고, 각 자식의 요구·보장과 조립 등식을 같은 바인딩에 대해 묶는다.

연결이 검증된 두 부품이 `s → t → u`로 전체 상태를 전달하는 간단한 경우에는 다음과 같다.

```text
R_AB(s)   = R_A(s)
E_AB(s,u) = ∃ t, E_A(s,t) ∧ E_B(t,u)
```

일반적인 합성 부품은 외부 입력과 요구를 명시하고, 그 요구 아래 모든 자식에 진입할 수 있음을
검사한다. 새 합성 부품을 만드는 경우 합성 `ensures`는 계산한 조건을 그대로 참조하거나,
Agent가 작성한 더 읽기 쉬운 조건을 사용할 수 있다. 후자의 경우 합성 부품의 요구 아래 두 조건의
동치 증명을 제공한다. 이미 계약이 있는 부모를 분해하는 경우에는 계산한 조건을 부모의 기존
`ensures`와 비교한다. 원하는 외부 계약을 적는 것으로 자식 계약이나 부모 계약의 의미를 덮어쓰지 않는다.

기본 부품의 생성기 작성과 soundness·completeness 증명이 끝나면 공통 정리로 합성 부품의
생성기 증명을 도출한다. 계획 단계에서 확인한 연결·조립·외부 계약 대응을 여기에 사용하며,
자식 생성기의 내부 증명을 다시 작성하지 않는다.

### 최종 목표와의 연결

최종 계획은 남은 `require` 없이 모든 premise를 보장해야 한다. 아래는 이를 기존 `root` 후보에
대응시키고 soundness와 completeness 방향을 나누어 적은 검토안이다.

1. 루트의 최종 `requires`는 비어 있거나 `True`다. 초기 정보를 사용한다면 그 근거도 최종 계획에
   포함하여, 사용자에게 새 가정을 요구하는 열린 계약으로 끝내지 않는다.
2. 루트의 최종 출력이 원래 `Contract.Input`이다.
3. Soundness 방향: 루트의 출력 조건에서 원래 `Contract.Premise`의 모든 조건이 따른다.
4. Completeness 방향: 원래 `Contract.Premise`를 만족하는 모든 입력을 루트의 출력 조건과
   조립으로 표현할 수 있다. 3만 확인해서 이 방향까지 성립한다고 보지 않는다.

이 대응을 생성기 구현 전에 계약만으로 확인할 수 있어야 한다. Agent가 직접 증명하거나,
여러 보조정리와 중간 계약의 동치를 연결하는 방법 모두 허용한다. 부품마다 원래 premise의 조건을
하나씩 배정하거나 정해진 분해 연산을 거치도록 강제하지 않는다.

보조 값은 최종 입력으로의 투영을 통해 다룬다. 모든 원래 유효한 입력을 만들 호환 가능한 내부
선택이 하나 이상 있으면 된다. 같은 최종 입력을 만드는 모든 보조 표현을 열거할 필요는 없지만,
각 부품의 계약이 허용한 출력은 그 부품의 completeness 대상이다.

### 증명 의무와 선언의 연결

도구가 의무의 ID, 소유 그룹 또는 연결, 정확한 명제를 도출한다. Agent는 그 명제를 증명하는
Lean 선언을 `evidence`에 연결한다. 일반적인 보조정리와 정의를 자유롭게 작성할 수 있다.
증명만 수행하는 실행 그룹은 만들지 않는다.

기본 부품에 조립 식이 있으면, 그 부품의 요구와 보장이 조립 등식도 보장하는지 검사한다.
이 조립 식은 해당 부품의 입력과 출력만 참조한다. 합성 부품에서는 조립 등식을 내부 연결 조건에
넣고, 내부 값을 양화한 조건과 외부 계약의 동치를 검사한다.

| 의무 | 붙는 곳 | 확인 시점 |
| --- | --- | --- |
| 첫 자식과 다음 자식의 요구 충족 | 합성 부품 안의 각 연결 | 계약을 분해·합성할 때 |
| 조립 대응 | 조립을 선언한 부품 | 계약을 분해·합성할 때 |
| 합성 조건과 부모의 외부 계약 동치 | 해당 합성 부품 | 계약을 분해·합성할 때 |
| 최종 require 해소·원래 premise와의 양방향 대응 | 루트와 목표의 연결 | 계약 확정 시 |
| 생성기 soundness·completeness | 기본 부품의 구현 | 해당 생성기를 작성한 뒤 |

합성 부품의 생성기 증명은 자식들의 구현과 증명에서 도출한다. 증명 선언이 없으면 의무는
미완료다. 계약·순서·입출력·조립·참조한 정의가 바뀌면 영향을 받는 명제와 증명을 다시 검사한다.
검사 결과와 소스 정체성을 도구가 계산하며 수작업 성공 표시나 해시 수정으로 인증하지 않는다.

### 작은 표현 예제

자연수 쌍 `x`에 대한 원래 premise를 `x의 첫 성분 < 둘째 성분 ≤ 10`으로 둔다.

| 부품 | 입력 | 출력 | requires | ensures |
| --- | --- | --- | --- | --- |
| A | 없음 | `a` | `True` | `a < 10` |
| B | `a` | `b` | `a < 10` | `a < b ≤ 10` |
| AB | 없음 | `a,b` | `True` | `a < 10 ∧ a < b ≤ 10` |
| Root | 없음 | `x` | `True` | `∃ a b, a < 10 ∧ a < b ≤ 10 ∧ x = (a,b)` |

```text
AB.members = [A, B]
A.order = 10
B.order = 20

Root.members = [AB]
AB.order = 10
Root.assembly = { x := (a,b) }
Plan.root = Root
Plan.target.output = x
```

AB는 자식이 만든 `a,b`를 그대로 외부에 제공한다. Root는 그 값으로 `x`를 조립하고,
자기 외부 계약에서는 `a,b`를 존재 양화한다. 생성 방법을 특정하지 않아도 이 연결을 표현할 수 있다.

같은 예를 부모 부품 C의 분해로 볼 수도 있다. C는 출력 `x`에 대해
`x.1 < x.2 ∧ x.2 ≤ 10`을 보장하며, `requires = True`다. C 안에 A와 B를 넣고
`x := (a,b)`로 조립한다고 할 때 세 의무는 다음과 같다.

1. A의 요구는 `True`이므로 바로 사용할 수 있다. A의 보장 `a<10`은 B의 요구를 충족한다.
2. A와 B가 계약에 맞는 `a,b`를 제공했다면 `a<b≤10`이므로 조립한 `(a,b)`는 C의 조건을 만족한다.
3. C가 허용하는 임의의 `x`에 대해 `a=x.1`, `b=x.2`를 고른다. `a<b≤10`에서 `a<10`도
   따르므로 A와 B의 계약을 모두 만족하고, 조립 결과는 정확히 주어진 `x`다.

여기서 3의 선택은 계약 대응을 증명하는 방법이다. 실제 생성 알고리즘이나 부품의 구현을 지정하지 않는다.
계약을 확정한 뒤 A와 B의 생성기를 각각 작성하고, 각 구현의 soundness·completeness를 증명한다.
그 후 이미 확인한 분해 의무와 공통 정리로 C의 생성기 증명을 얻는다.

A가 `a≤10`을 허용한다면 `a=10`에서 B의 요구를 충족하지 못하므로 1을 증명할 수 없다.
A가 짝수 `a`만 허용한다면 1과 2는 만족할 수 있지만, C가 허용하는 `(1,2)`를 표현하지 못하므로
3을 증명할 수 없다. 부모 C의 계약을 바꾸지 않았다면 이 문제는 해당 분해 경계에서 드러난다.

반대로 부모 계약을 미리 고정하지 않고 자식들로부터 새 루트 계약을 계산했다면, 짝수 제한은
최종 루트와 원래 premise의 동치 검사에서 드러난다.

### 구조 검사와 상태

도구가 기계적으로 확인할 사항은 다음과 같다.

- 모든 ID·타입·표현식 참조가 해석되고, 변수 범위가 맞는다.
- 그룹의 포함 관계에 순환·중복 실행이 없고, 형제 그룹의 `order`가 중복되지 않는다.
- 입력과 조립에 필요한 값이 해당 시점에 보이며, 독립적인 중복 생성자가 없다.
- 합성 부품의 경계를 넘어 쓰는 값은 입출력으로 제공된다. 내부 값이 외부 계약에 자유롭게 남지 않는다.
- 조립에 필드 누락·잘못된 생성자 연결·순환이 없고, 최종 출력의 타입이 원래 입력 타입과 맞는다.
- 원래 식의 논리 구조를 보존한다. 대안 아래의 조건을 무조건적인 사실로 사용하지 않는다.
- 참조된 증명 선언의 타입이 도출한 의무와 정확히 일치한다.

구조 검사는 계약의 진실성을 대신하지 않는다. 함의와 동치, 생성기 정확성은 Lean 증명으로
확인한다. 어려운 증명이나 구체적인 생성 방법을 도구가 일반적으로 자동 발견한다고 가정하지 않는다.

자료구조는 작성 중인 계획도 표현한다. 생성기나 증명 참조가 없는 상태를 허용하되 완료로 취급하지 않는다.
상태는 저장된 선언과 검사 결과에서 도출한다.

| 상태 | 의미 |
| --- | --- |
| 계획 작성 중 | 계약·조립·설명·증명 참조를 수정 중이며 미완료 항목이 있음 |
| 계약 검증 완료 | 구조, 계약 연결, 조립, 외부 계약과 최종 목표 대응이 검증됨 |
| 부품 구현 검증 완료 | 기본 부품의 생성기와 soundness·completeness가 검증됨 |
| 전체 인증 완료 | 조합한 생성기가 기존 `check`를 통과함 |

계약을 확정한 뒤에는 같은 계약 아래 부품을 구현한다. 변경이 필요하면 변경된 경계와 영향을
명시하고 관련 검증을 다시 수행한다. 모든 명세에서 처음 고른 분해가 바로 구현 가능하다는 보장은
하지 않는다. 생성 가능성과 구현 방법을 충분히 고려하게 하는 지침은 별도로 구체화한다.

### 기존 기반과 구현 경계

[Staged.lean](../properties/wasm_module_ok/Staged.lean)에는 `Stage`, `always`, `sound`,
`complete`, `compose`, `computeStage`가 있다. 기존 코드와 Palamedes의 `Gen` 조합 규칙을
기반으로 삼되 그대로 동일한 인터페이스라고 보지는 않는다. 기존 `always`는 출력 존재를 요구하지만
새 계획 구조에서는 필수 의무로 두지 않는다. `chain_support_iff`의 증명은 `always`를 사용하지
않으므로 support 대응에 필요한 증명과 비어 있지 않음의 증명을 분리할 수 있다.
또한 현재 `compose`는 경계 조건의 동치를 받지만, 위 순차 연결 후보에는 필요한 방향의
함의면 충분하다. 실제 공통 기능으로 옮길 때 이 차이들을 반영하고 회귀 검사한다.

기존 `scripts.property plan`은 외부 관측과 입력 출처를 분석하는 도구다. 이 문서의 범용 생성
계획 자료구조는 아직 구현되지 않았다. 생성 코드가 없는 계약과 구현 참조를 분리해 표현하고,
계약만 조합하는 단계와 생성기까지 조합하는 단계가 같은 그룹 구조를 사용하도록 한다.

최종 결과는 원래 `Contract.generatorSound`와 `Contract.generatorComplete`를 제공하고
기존 `emit/check/run`으로 검사한다. 생성 산출물 재구성, 증명·실행 코드·전송·신선도 감사를
유지한다. 계획 파일은 증명이나 인증서를 대신하지 않는다. 전체 `Proof.lean`과 `Generator.lean`의
분리, 변경 후 재인증 등 저장소의 `AGENTS.md` 규칙을 따른다.

자료구조 구현 시에는 작은 쌍 예제로 기본 부품과 합성 부품의 동일한 인터페이스를 확인한다.
내부 값의 보존·숨김, 잘못된 배선, 이중 생성, 누락된 증명, 오래된 계약 참조, 원래 입력을 줄인
계약이 각각 알맞은 검사에서 드러나야 한다. 생성 계획의 품질을 판단하는 별도 정책이나 새로운
분해 작업 목록을 이번 자료구조에 포함하지 않는다.
