# Premise를 만족하는 생성기의 분해 계획

## 목표

Premise를 만족하는 입력만 만들고, 그런 입력을 빠짐없이 만드는 생성기를 작은 단계로 나누어 작성한다.
생성한 값을 검사해서 버리는 거절 생성에는 의존하지 않는다.

분해의 핵심은 다음 한 문장이다.

> 생성은 앞에서부터 실행하고, 각 단계가 요구하는 조건은 뒷부분부터 작성해 앞 단계로 전달한다.

단계 사이를 잇는 것은 서로의 생성기가 아니라 이 조건이다. 조건이 모두 정해지면 각 단계의 생성기와
증명은 서로 기다리지 않고 작성할 수 있다.

**분해가 문제를 항상 쉽게 만들지는 않는다.** 어떤 단계의 조건이 원래 premise만큼 복잡하면 분해는
어려움을 옮긴 것에 그친다. 이 계획은 그런 지점을 생성기 작성 전에 드러내는 것을 목표로 한다(§3.5).

## 1. Premise를 역할로 나눈다

각 premise를 생성 관점에서 세 역할 중 하나로 분류한다.

| 역할 | 뜻 | `Module_ok`의 예 |
| --- | --- | --- |
| 고르기 | 생성기가 새로 결정하는 값 | 타입·import·global 목록, 함수 본문 명령어 |
| 계산하기 | 이미 정해진 값에서 자동으로 나오는 값 | `C_1`(`C_0`에 import 정보를 더함), `free = $free_module(module')` |
| 검사하기 | 관련 값이 모두 정해진 뒤 확인하는 조건 | export 이름 중복 금지, 블록 끝 스택 타입 일치 |

분류 후 두 원칙을 따른다.

- 여러 부분이 공유하는 값은 먼저 고르지 않는다. 부품을 고른 뒤 계산으로 얻어 다음 단계에 넘긴다.
  공유 값을 먼저 고르려면 가능한 공유 값을 미리 알아야 한다. `Module_ok`의 컨텍스트 `C_0 … C_8`처럼
  공유 값이 부품의 요약이면, 가능한 공유 값을 아는 일은 원래 문제와 같다.
- 검사는 그 검사에 나오는 값 중 마지막으로 정해지는 값을 고르는 단계로 흡수한다. 그 단계는 검사를
  통과하는 선택지 중에서만 고른다. 예를 들어 export 이름은 아직 쓰지 않은 이름 중에서, 다음 명령어는
  현재 스택에서 실행할 수 있는 명령어 중에서 고른다.

## 2. 생성 순서를 정하고 순환을 끊는다

각 premise가 어떤 값을 읽고 어떤 값을 정하는지 보고, "먼저 정해져야 하는 값"을 화살표로 잇는다.
화살표를 따라 정한 순서가 생성 순서다.

서로가 서로를 먼저 필요로 하는 순환이 있으면 순서를 정할 수 없다. 순환을 끊는다는 것은 화살표 하나가
실제로는 필요 없음을 보이는 것이다. 순환을 만드는 검사를, 의미가 같으면서 그 값을 읽지 않는 조건으로
바꾸고 두 조건이 같음을 증명한다.

```text
global 단계 ──필요──▶ REFS     (Instr_ok/ref.func의 검사 x ∈ C.REFS.FUNCS)
REFS        ──필요──▶ global   (REFS = $free_module(module')는 global이 정해져야 계산됨)
```

`x`는 그 global의 초기값 안에 있고, `$free_module`은 global을 포함한 `module'`에 나오는 함수 번호를
모두 모은다. 따라서 함수 본문 밖에서 `x ∈ C.REFS.FUNCS` 검사는 항상 참이며, 이 검사를 "참"으로 바꿔도
의미가 같다. 첫 화살표가 사라지므로 `global → REFS 계산 → 함수 본문` 순서가 생긴다.

순환을 끊는 조건을 찾지 못하면 순환에 걸린 단계를 한 단계로 합친다. 결과는 올바르지만 분해의 효용은
줄어든다.

## 3. 뒷부분부터 입장 조건을 작성해 앞으로 전달한다

### 3.1 입장 조건

단계 k의 입장 조건은 단계 k에 들어오는 상태에 대한 조건이다. 이 조건을 만족하는 상태에서는 다음 두
가지를 함께 지키는 값을 항상 고를 수 있어야 한다.

- 단계 k 자신의 조건(흡수한 검사 포함)
- 내보내는 상태가 단계 k+1의 입장 조건을 만족함

### 3.2 작성 절차

1. 마지막 단계의 입장 조건을 작성한다. 뒤에 단계가 없으므로 자기 조건만 본다.
2. 그 조건을 바로 앞 단계에 전달한다. 앞 단계는 자기 조건과 전달받은 조건을 함께 지킬 수 있는 상태를
   자신의 입장 조건으로 작성한다.
3. 첫 단계까지 반복한다.
4. 시작 상태가 첫 단계의 입장 조건을 만족하는지 확인한다. 만족하지 않으면 premise에 해가 없다고 보고한다.

### 3.3 예

```text
단계 1: a ≥ 1, b ≥ 1 고르기            → c = a + b 계산
단계 2: d ≥ 1, 짝수 e ≥ 2 고르기, d + e = c
단계 3: 홀수 f 고르기, 3 ≤ f < e
```

| 작성 순서 | 단계 | 자기 조건 | 전달받은 조건 | 입장 조건 |
| --- | --- | --- | --- | --- |
| 1 | 3 | 홀수 f, 3 ≤ f < e | 없음 | e ≥ 4 |
| 2 | 2 | d ≥ 1, 짝수 e ≥ 2, d + e = c | e ≥ 4 | c ≥ 5 |
| 3 | 1 | a ≥ 1, b ≥ 1 | c ≥ 5 | 항상 |

생성은 앞에서부터 실행한다. 각 단계는 자기 조건과 다음 단계의 입장 조건을 함께 지키는 값만 고른다.

```text
단계 1: a, b ≥ 1 이고 a + b ≥ 5 인 쌍 고르기, c := a + b
단계 2: 4 ≤ e ≤ c - 1 인 짝수 e 고르기, d := c - e
단계 3: 3 ≤ f < e 인 홀수 f 고르기
```

각 단계에 들어오는 상태는 그 단계의 입장 조건을 이미 만족하므로, 어느 단계에서도 고를 값이 없어지지 않는다.

### 3.4 뒷부분부터 작성하는 이유

단계 k를 작성할 때 그 뒤 단계의 입장 조건은 이미 정해져 있으므로 각 단계를 한 번만 작성한다.
앞 단계를 고치는 일은 선택지를 줄이는 것뿐이어서, 이미 작성한 뒤 단계의 입장 조건을 깨뜨리지 않는다.

앞에서부터 작성하면 위 예의 단계 1을 `a + b ≥ 2`로 쓴 뒤 `a + b ≥ 3`, `a + b ≥ 5`로 두 번 고쳐야 한다.
단계가 많을수록 앞쪽 단계를 고치는 횟수가 늘어난다.

### 3.5 입장 조건을 구하기 어려운 경우

단계가 한 줄로 이어진 부분에서는 3.2 절차가 한 번에 끝난다. 목록이나 재귀처럼 같은 단계가 반복되는
곳에서는 "나머지를 끝낼 수 있는가"라는 질문이 자기 자신을 다시 가리킨다.

| 경우 | 처리 |
| --- | --- |
| 항상 쓸 수 있는 끝내기가 있음(빈 목록, `unreachable`) | 입장 조건은 "항상"이다 |
| 끝내기가 없고 상태가 유한함 | 회차마다 넓혀 가는 반복으로 계산한다. 생성기가 실행 중에 계산하는 값이며, 증명은 회차에 대한 귀납이다 |
| 끝내기가 없고 상태가 무한함 | `c ≥ 5` 같은 닫힌 형태를 찾아야 한다. 이 분해로 사라지지 않는 실제 어려움이다 |

입장 조건이 원래 premise만큼 복잡해지면 그 경계는 나쁜 경계다. 그 단계와 다음 단계를 합치고 3.2 절차를
다시 적용한다. 이 판단은 생성기를 작성하기 전에 내린다.

## 4. 단계별 생성기와 증명을 작성하고 조합한다

입장 조건이 모두 정해지면 각 단계의 할 일은 다음 문장으로 고정된다.

> 입장 조건을 만족하는 상태에서, 자기 조건과 다음 단계의 입장 조건을 함께 지키는 값을 빠짐없이,
> 그리고 그런 값만 고른다.

각 단계에서 세 가지를 증명한다.

| 증명 | 내용 | 입장 조건이 틀렸을 때 |
| --- | --- | --- |
| 항상 고를 수 있음 | 입장 조건 아래에서 고를 값이 하나 이상 있다 | 조건이 너무 약하면 실패한다 |
| soundness | 고른 값은 자기 조건과 다음 단계의 입장 조건을 지킨다 | |
| completeness | 유효한 입력에 나오는 값은 모두 고를 수 있다 | 조건이 너무 강하면 유효한 입력이 빠져 실패한다 |

두 실패 조건 때문에 증명을 통과하는 입장 조건은 정확한 조건뿐이다. 잘못 작성한 조건은 증명에서 드러난다.

단계들은 서로의 생성기에 의존하지 않으므로 어떤 순서로든, 병렬로도 작성할 수 있다.

조합은 property마다 새로 증명하지 않는다. "각 단계가 세 증명을 만족하면 이어 붙인 생성기는 sound하고
complete하며 막히지 않는다"는 정리를 한 번 증명해 재사용한다. Completeness는 다음과 같이 이어진다.
유효한 입력 하나를 같은 순서로 고른다고 보면, 각 중간 상태는 입장 조건을 만족하고 그 입력의 선택은
허용된 선택지 안에 있다.

최종 생성기는 기존 `generatorSound`와 `generatorComplete` 검증을 통과해야 한다.

## 5. 역할 분담

| 작업 | 담당 |
| --- | --- |
| premise 역할 분류, 의존 화살표, 생성 순서 | 도구 |
| 순환 탐지, 순환을 만드는 검사 지목 | 도구 |
| 순환을 끊는 대체 조건과 동치 증명 | AI가 제안하고 Lean이 확인 |
| 대체 조건이 없을 때 단계 합치기 | 도구 |
| 입장 조건 작성(뒷부분부터) | AI가 작성하고 Lean이 확인 |
| 단계별 생성기와 세 증명 | AI가 작성하고 Lean이 확인 |
| 단계 조합 | 한 번 증명한 정리를 도구가 적용 |
| 막힌 단계와 단계 합치기 결정 검토 | 사용자 |

AI는 도구가 지목한 검사와 단계에 대해서만 답한다. AI가 틀린 조건을 내면 Lean 증명이 실패하고, 답을 내지
못하면 해당 단계가 막힌 것으로 보고된다. 반복해서 나타나는 순환 끊기 유형(자기 안에 나온 값을 모은 집합에
대한 검사 등)은 별도 도구 작업에서 도구 규칙으로 옮길 수 있다.

## 6. `Module_ok` 적용안

### 생성 순서

```text
타입 → import → 함수 헤더 → table · mem · global · tag · elem · data → start → export
  → REFS 계산 → 함수 본문
```

- `Func_ok`는 본문을 보지 않고 함수 타입만 컨텍스트에 더한다. 본문은 `Funcbody_ok`가 `C_8`에서 따로
  검사하므로 명세가 이미 헤더와 본문을 나눠 두었다.
- `REFS`는 §2의 방식으로 순환을 끊고 함수 본문 직전에 계산한다. 함수 본문에서 `ref.func x`는 `x ∈ REFS`인
  경우에만 고른다.

### 입장 조건(뒷부분부터)

| 작성 순서 | 단계 | 입장 조건 | 근거(증명할 것) |
| --- | --- | --- | --- |
| 1 | 함수 본문 | 항상 | `unreachable` 하나로 블록 끝 조건을 만족한다 |
| 2 | export | 항상 | 빈 목록 |
| 3 | start | 항상 | 없음(`eps`) |
| 4 | data, elem, tag, global, mem, table | 항상 | 빈 목록 |
| 5 | 함수 헤더, import, 타입 | 항상 | 빈 목록 |

모듈 단계 사이에는 전달되는 조건이 없다. 조건이 생기는 곳은 원소 하나를 만드는 단계의 안쪽이다.

- global 하나, table 하나: 타입을 고른 뒤 초기값을 고른다. 초기값 단계의 입장 조건은 "이 타입을 상수식으로
  채울 수 있음"이며, 타입 단계는 채울 수 있는 타입만 고른다.
- elem 하나: 초기값 목록이 비어 있을 수 있으므로, 목록이 비어 있지 않을 때만 같은 조건이 필요하다.
- 함수 본문의 근거는 `$pop`과 `$push` 절을 따라가면 성립하며, `BotT`가 모든 값 타입에 매칭된다는 사실이
  필요하다.

기존 결정 방향 보조정리(`properties/wasm_module_ok/Validity.lean`과 `*Validation.lean`)는 각 단계의 자기
조건을 풀어 쓰고, 검사를 통과하는 선택지를 판정하는 데 재사용한다.

### 남는 실제 어려움: 상수식으로 채울 수 있는 타입

`Const_ok`는 모든 명령어에 `$is_const`를 요구하고, `unreachable`은 상수 명령어가 아니다. 따라서 null이 될
수 없는 참조 타입에는 상수식이 없을 수 있다.

```text
$a = struct { i32 }       → 1회차: i32 상수로 채울 수 있음
$b = struct { ref $a }    → 2회차: $a를 채울 수 있으므로 가능
$c = struct { ref $c }    → 채울 수 없음
```

채울 수 있는지는 컨텍스트의 타입·함수·global에 달려 있다. 후보 타입이 유한하므로 §3.5의 유한 반복으로
계산할 수 있을 것으로 본다. 이 부분을 별도 부분 문제로 먼저 확인한다.

## 작업 순서

| 순서 | 작업 | 결과 |
| --- | --- | --- |
| 1 | premise 역할 분류, 의존 화살표 | 생성 순서 후보, 순환 목록 |
| 2 | 순환 끊기 또는 단계 합치기 | 확정된 생성 순서 |
| 3 | 입장 조건 작성(뒷부분부터) | 단계별 할 일 확정, 해 없음 보고, 또는 단계 합치기 |
| 4 | 조합 정리(한 번) | 재사용할 조합 정리 |
| 5 | 단계별 생성기와 증명(독립, 병렬 가능) | 단계별 완료 |
| 6 | 조합 적용과 `check` | 전체 생성기 인증 |

`Module_ok`에서는 3단계에 들어가기 전에 상수식 채우기 문제가 유한 반복으로 끝나는지 먼저 확인한다.

이 문서는 설계안이며 구현·검증 완료를 의미하지 않는다.
